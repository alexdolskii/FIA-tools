# Схемы экспериментов — 96 лунок

Помогай оформить уже определённый эксперимент без изменения его научного смысла. Используй один общий формат схемы, а не независимые схемы FIA и UMA. Проверяй поддержку этого формата конкретным потребителем отдельно.

## Правила согласования

- Обсуждай **любое изменение** до его внесения: названия, пробелы, координаты, цвета, жирный шрифт, порядок, объединение условий, каналы, методы, исключения и техническую структуру.
- Сначала исследуй исходник и подготовь конкретное предложение. Не спрашивай разрешения на чтение или проверку.
- Уточняй все существенные неопределённости. Не превращай неизвестное значение в пустую ячейку, `Ignore`, контроль, исключённую лунку или предполагаемый канал.
- Используй уже полученные ответы в текущем задании. Не проси повторно согласовать неизменившийся и уже одобренный план.
- Для нового файла сначала покажи конкретное расположение и назначения текстом или компактной таблицей и получи согласие, если они ещё не согласованы.
- Не создавай итоговый XLSX до разрешения неоднозначностей и согласования изменений. Неполный исходник можно разобрать и обсуждать без готового файла. Не применяй предположение по истечении времени ожидания.
- Не меняй код FIA/UMA, не открывай PR и не запускай анализ микроскопических изображений в рамках этого навыка.

## 1. Определи режим и исходники

Выбери из запроса: **проверка**, **исправление/преобразование** или **создание по описанию**. Если режим неясен, начни с проверки и уточни ожидаемый результат.

Принимай уже заполненную, потенциально правильную схему как самостоятельный вход для проверки. Запросы «всё ли правильно», «проверь готовую схему» и «можно ли использовать этот файл» не означают запрос на исправление или создание нового файла. Не предполагай наличие ошибок и не предлагай обязательную переделку только потому, что оформление отличается от шаблона, если контракт соблюдён.

Работай только с планшетами 8 × 12, A–H и 1–12. Для другого размера сообщи об ограничении и уточни задачу; не обрезай и не перенумеровывай лунки.

Принимай только необходимые материалы: Excel, скриншоты, фотографии, PDF, рукопись и текст. Не требуй все типы файлов. Если сведения противоречат друг другу, покажи расхождение пользователю.

Для извлечения из изображений/PDF и подготовки вопросов прочитай [review-workflow.md](references/review-workflow.md). В Excel исследуй точные координаты, значения, прямые заливки, жирность, формулы, объединения и назначение листов; не ограничивайся видимыми подписями.

Установи потребителя и версию: FIA, UMA, оба или подготовка общего формата без запуска. Не спрашивай повторно, если это уже известно.

## 2. Проверь контракт и совместимость

Прочитай [schema-contract.md](references/schema-contract.md) и компактный [compatibility.json](references/compatibility.json). Используй `assets/96_well_universal_template.xlsx` как структурный шаблон, а не как заполненный эксперимент.

Базовая проверка соответствует конкретному снимку новой схемы FIA. Это **не доказательство совместимости с текущей установленной версией**, веткой `tech_dev` до включения изменений или UMA. Переименование файла не добавляет поддержку формата.

Если целевой коммит совпадает с проверенным, не перечитывай весь репозиторий. Если версия изменилась, адресно проверь контракт, загрузчик схемы и правила поиска файла. Для FIA начни с `docs/PLATE_SCHEME.md` и `fia-tools/plate_design.py`; для UMA найди соответствующий загрузчик в выбранной версии. Используй доступный GitHub-коннектор или локальный checkout. Не меняй репозитории. Не используй названия веток как неизменные версии.

Поддержка UMA общего формата на момент создания навыка **не проверена**. Пользователь планирует её добавить. Не экспортируй старый UMA Order/Group формат вместо общего. Если поддержка отсутствует, объясни ограничение, а общий XLSX подготовь только с согласованным назначением и явным статусом совместимости. Не добавляй второй файл другого формата автоматически.

## 3. Проверь эксперимент и согласуй план

Сопоставь исходник с представлением: эксперимент, лунка, условие, блок, контроль, исходные C1–C4, метод и имя маркера, явно запрошенные пересечения, положение панелей и порядок условий. Сохраняй отдельно исходную запись и предложенное толкование. Даже если загрузчик обрезает пробелы, не переписывай названия без согласования.

Проверь:
- физические лунки и ориентацию; занятые, незадействованные и явно исключаемые лунки;
- непротиворечивость условий, контрольных ролей и блоков;
- число и порядок каналов для каждого варианта окрашивания;
- метод каждого канала и точное имя маркера;
- различие `Ignore` и отсутствующего канала;
- только явно заданные допустимые пересечения Foci;
- соответствие `PLOT LAYOUT` условиям, заливкам и контролям;
- число лунок на условие для общего ядерного маршрута и каждого маркера отдельно.

Не выводи метод из имени маркера: например, pSMAD2 может требовать уточнения между Foci и Nuclear intensity. Не выводи контроль только из слова Control. Не переноси назначения прошлой схемы на новый эксперимент: C1 не всегда ядра, C2 не всегда Fibronectin, C3 не всегда маркер.

Не объединяй одинаковые воздействия с разными окрашиваниями автоматически. Если это соответствует задаче, предложи объединение для общего ядерного отчёта и объясни, какие лунки будут объединены. Маркерные подмножества сохраняй раздельными.

Покажи компактно: ошибки, неясные места, точные предлагаемые изменения и вопросы. Ссылайся на лунки/ячейки. Не повторяй полный опрос, если исходник уже содержит ответы.

В режиме проверки сверяй все 96 позиций и для доступного XLSX запускай проверки из раздела 5 **на исходном файле**, без перезаписи или повторного экспорта. Не ограничивайся визуальным осмотром. Для изображения/PDF/текста проверяй доступные сведения и явно укажи, что внутреннюю структуру Excel без самого XLSX проверить нельзя.

Заверши проверку одним из выводов с указанием проверенного объёма: **«Ошибок не найдено»**, **«Найдены ошибки»** или **«Полная проверка невозможна: нужны уточнения»**. Разделяй обнаруженные ошибки, неоднозначности, предупреждения о дизайне и неподтверждённую совместимость. Не называй неизвестную версию программы ошибкой самой схемы; выполни доступную проверку структуры и отдельно обозначь ограничение. Не объявляй эксперимент научно корректным или файл готовым к запуску только по успешной структурной проверке.

Если ошибок и неоднозначностей в проверенных данных нет, прямо сообщи, что исправления не требуются. Не создавай новый XLSX и не проси повторно подтвердить однозначно записанные сведения. Если проблемы обнаружены, укажи лунки/ячейки и необходимые уточнения или предлагаемые исправления, сохранив файл без изменений. Переходи к исправлению только после согласования. В остальных режимах дождись согласования плана и затем переходи к созданию.

## 4. Создай согласованный XLSX

Используй доступный навык Spreadsheets и его текущие инструменты для авторинга и визуальной проверки. Для PDF используй соответствующий навык по необходимости. Сохрани координаты входных областей и прямое форматирование из контракта.

Создай **один итоговый `.xlsx` на эксперимент**. Используй английские фиксированные имена листов и методов. Сохрани язык и написание пользовательских условий/маркеров, если перевод или переименование не согласованы. Обсуждай задачу на языке пользователя.

Сохрани исходник. При преобразовании отдельной UMA-схемы в общий формат создай новый файл, не заменяя исходную рабочую UMA-схему. Если пользователь явно редактирует существующий итоговый файл, используй его идентичность и версионирование согласно навыку Library. Не создавай дополнительные варианты, PDF, JSON или отдельные журналы без запроса.

Для проверенного FIA-потребителя используй имя `FIA_<experiment>.xlsx` и размещение рядом с сырыми изображениями, не в `fia_assay`. Для UMA/обоих сначала проверь правила поиска файла. При конфликте префиксов объясни его: один файл нельзя объявить автоматически обнаруживаемым обеими программами без поддержки этого в коде.

## 5. Проверь итог до выдачи

Сверь **все 96 позиций**. Подтверди сохранение исходных использованных лунок и всех согласованных изменений. Проверь контроль, блок, метод, маркер и исходный канал для каждого назначения; пустые неиспользованные лунки и отсутствующие каналы; панели и пересечения.

Запусти автономную проверку сохранённого XLSX:

```bash
python <skill-root>/scripts/validate_scheme.py /absolute/path/FIA_experiment.xlsx
```

Для запроса статистических сравнений добавь `--require-controls`. Скрипт только читает файл, проверяет фиксированный контракт, печатает JSON в терминал и возвращает ненулевой код при структурной ошибке. Не сохраняй этот JSON отдельным пользовательским результатом без запроса.

Если доступен проверенный загрузчик выбранной версии FIA, также проверь его:

```bash
python <skill-root>/scripts/validate_scheme.py /absolute/path/FIA_experiment.xlsx --parser /absolute/path/fia-tools/plate_design.py
```

Не запускай произвольный код из входных файлов. `--parser` используй только с адресно проверенным кодом целевого репозитория. Для UMA используй реальную проверку её потребителя; не выдавай проверку FIA за проверку UMA.

Отдельно покажи ограничения дизайна: одна лунка на условие для маркера не позволяет оценить внутригрупповую вариацию при сравнении по лункам. Не объявляй изображения или ядра независимыми биологическими повторами. Малое число лунок — предупреждение о дизайне, а не причина добавлять лунки или менять назначения.

Визуально проверь каждый изменённый лист и затем экспортированный файл загрузчиком. Не добавляй скрытые формулы или условное форматирование во входные области.

Сохрани итог согласно правилам Library и дай ссылку. Кратко перечисли согласованные изменения, проверенную версию/контракт и ограничения. Различай: структура проверена; целевой загрузчик проверен; соответствие реальным изображениям проверено. Последнее указывай только после отдельной разрешённой сверки с данными. Схема сама по себе не подтверждает число каналов или наличие изображений в эксперименте.
